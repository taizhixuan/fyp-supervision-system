# Facts — 5.1 Deployment

> Existing 5.1 prose already exists in `chapter5.md:15–74`. Some claims
> there are stale (XGBoost in ai-recommendation, Flan-T5 as the chatbot
> generator). This facts file captures the **current** deployment shape

## Files involved

| File | Role |
|---|---|
| `docker-compose.yml` | Production-style stack — six services, named volumes, single bridge network |
| `docker-compose.override.yml` | Auto-merged dev override; swaps the frontend to Vite dev mode with HMR on port 5173 |
| `backend/Dockerfile` | Multi-stage Maven build → Temurin JRE 17 runtime |
| `frontend/Dockerfile` | Multi-stage Node build → nginx:alpine serve |
| `frontend/Dockerfile.dev` | Single-stage Node 20 dev container running `npm run dev` |
| `frontend/nginx.conf` | SPA fallback + gzip; `/api` returns 404 (frontend talks to backend directly) |
| `frontend/vite.config.ts` | Dev port 3000 + `/api` and `/uploads` proxies to `:8080`, polling on |
| `ai-recommendation/Dockerfile` | python:3.11-slim, pre-downloads `BAAI/bge-base-en-v1.5` and `all-MiniLM-L6-v2`, gunicorn `--preload --workers 1 --threads 4` |
| `ai-proposal-analyzer/Dockerfile` | python:3.11-slim, gunicorn `--preload --workers 1 --threads 4 --timeout 180` |
| `ai-chatbot/Dockerfile` | python:3.11-slim, pre-downloads `all-MiniLM-L6-v2` + `google/flan-t5-small`, builds the FAISS index on image build (`if [ ! -f vector_store/index.faiss ]; then python build_knowledge_base.py; fi`) |
| `backend/src/main/resources/application.yml` | Runtime config; env-var-driven |
| `backend/src/main/resources/application-dev.yml` | Profile overrides — `show-sql: true`, DEBUG logging |

## Services in the Compose stack

| Service | Image / build | Internal port | Host port | Volumes mounted | Healthcheck |
|---|---|---|---|---|---|
| `db` | `mysql:8` | 3306 | **3307** | `mysql_data:/var/lib/mysql` | `mysqladmin ping`, every 10 s, 5 retries |
| `backend` | build `./backend` (multi-stage Maven → Temurin 17 JRE) | 8080 | 8080 | `upload_data:/app/uploads` | depends on `db` `service_healthy` |
| `ai-recommendation` | build `./ai-recommendation` (python:3.11-slim) | 5001 | 5001 | `recommendation_models:/app/models` | none |
| `ai-proposal-analyzer` | build `./ai-proposal-analyzer` (python:3.11-slim) | 5002 | 5002 | `analyzer_models:/app/models` | none |
| `ai-chatbot` | build `./ai-chatbot` (python:3.11-slim) | 5003 | 5003 | `chatbot_vector_store:/app/vector_store` | none |
| `frontend` (prod) | build `./frontend/Dockerfile` (Node 20 build → nginx:alpine) | 80 | **3000** | none | depends on `backend` |
| `frontend` (dev override) | build `./frontend/Dockerfile.dev` | 3000 | **5173** | bind-mount `./frontend:/app` + anonymous `node_modules` | `VITE_USE_POLLING=true` |

All services share one user-defined bridge network: `fyp-network`.

## Named volumes

```
mysql_data              — MySQL data files
upload_data             — backend uploads (profiles, announcements, documents, reports, backups)
recommendation_models   — preserved model artefacts for ai-recommendation
analyzer_models         — preserved model artefacts for ai-proposal-analyzer
chatbot_vector_store    — FAISS index + JSON metadata sidecar for ai-chatbot
```

Rebuilding an image does not invalidate any of these volumes. Dropping
them deliberately requires `docker-compose down -v`.

### AI services

`ai-recommendation`:
- `FLASK_PORT=5001`
- `REC_EMBED_MODEL` default `BAAI/bge-base-en-v1.5` (768-dim, ~110 MB); fallback `all-MiniLM-L6-v2` is also baked into the image
- Optional weight overrides (`REC_W_SEMANTIC`, `REC_W_INTEREST`, `REC_W_SKILL`, `REC_W_PROGRAMME`, `REC_W_AVAILABILITY`)

`ai-proposal-analyzer`:
- `FLASK_PORT=5002`
- LLM provider chain (first match wins): `LLM_API_KEY` (+ `LLM_BASE_URL`, `LLM_MODEL`) → `GROQ_API_KEY` → `OPENAI_API_KEY`
- All three unset → NLP-only

`ai-chatbot`:
- `FLASK_PORT=5003`
- `USE_LOCAL_GEN="false"` — Flan-T5 is **off by default** at the compose level
- Same LLM provider chain as the analyzer

### Frontend

Build-time arg (production image):
- `VITE_API_BASE_URL` defaults to `http://localhost:8080/api`, baked into the bundle at `npm run build`

Dev override:
- `VITE_API_BASE_URL=http://localhost:8080/api`
- `VITE_USE_POLLING=true` (Windows-mounted volumes don't propagate inotify)

## Build pipelines per Dockerfile

### Backend (`backend/Dockerfile`)
Multi-stage:
1. `maven:3.9-eclipse-temurin-17` — `mvn dependency:go-offline -B`, then `mvn package -DskipTests -B` to produce `target/*.jar`
2. `eclipse-temurin:17-jre` — copies the fat JAR, `mkdir -p /app/uploads`, `EXPOSE 8080`, runs `java -jar app.jar`

### Frontend prod (`frontend/Dockerfile`)
Multi-stage:
1. `node:20-alpine` — `npm ci`, copy source, accept `VITE_API_BASE_URL` build-arg, `npm run build`
2. `nginx:alpine` — copy `dist/` into `/usr/share/nginx/html`, copy `nginx.conf` into `/etc/nginx/conf.d/default.conf`, `EXPOSE 80`

`nginx.conf` (final):
- SPA fallback: `try_files $uri $uri/ /index.html`
- `location /api` returns 404 (the frontend hits the backend directly via `VITE_API_BASE_URL`, not through nginx)
- gzip enabled for plain text, CSS, JSON, JavaScript, XML

### Frontend dev (`frontend/Dockerfile.dev`)
Single stage on `node:20-alpine`. Installs deps via `npm ci`, exposes 3000, runs `npm run dev -- --host 0.0.0.0 --port 3000`. Source is bind-mounted from the host so edits hot-reload.

### AI services (all three)
Same pattern: `python:3.11-slim` → `apt-get install build-essential` → `pip install -r requirements.txt` → copy source → `EXPOSE <port>` → `gunicorn --bind 0.0.0.0:<port> --preload --workers 1 --threads 4 --timeout 180 app:app`.

`--preload` loads the models in the master process *before* forking, so the model weights aren't duplicated across worker processes.

`ai-recommendation` and `ai-chatbot` additionally pre-download model
weights at image build time (`RUN python -c "from sentence_transformers import SentenceTransformer; ..."`)
so that the first request doesn't pay the download cost.

`ai-chatbot` also runs `build_knowledge_base.py` during image build if
`vector_store/index.faiss` is missing.

## Network topology

One private bridge network: `fyp-network` (driver: bridge).

Inter-service hostnames are the compose service names. The backend
reaches the AI services as `http://ai-recommendation:5001`,
`http://ai-proposal-analyzer:5002`, `http://ai-chatbot:5003`. The
frontend (browser) talks to the backend via the **host port** 8080,
not via the internal name — the JWT origin is set by `VITE_API_BASE_URL`
at build time.

Host-exposed ports (everything else stays on the internal network):

```
3000 → frontend (production nginx)        [overridden to 5173 in dev]
8080 → backend (Spring Boot)
3307 → MySQL (mapped to container 3306 to avoid clashing with host MySQL)
5001 → ai-recommendation
5002 → ai-proposal-analyzer
5003 → ai-chatbot
```

## Backend runtime config (`application.yml`)

- `server.port: 8080`
- `server.servlet.context-path: /api` — every endpoint is at `http://host:8080/api/...`
- HikariCP: `maximum-pool-size: 10`, `minimum-idle: 5`
- JPA: `ddl-auto: validate` (Flyway owns the schema; Hibernate refuses to boot on drift)
- Flyway: `baseline-on-migrate: true`, scans `classpath:db/migration`
- Multipart: 50 MB file / 50 MB request limits
- Jackson: dates as ISO-8601 strings, nulls omitted
- Mail: SMTP starttls on `MAIL_HOST:MAIL_PORT`, gated by `app.email.enabled`
- App: JWT secret + 24 h expiry; AI URLs as above; push notifications via VAPID keys (off by default)
- Logging baseline `INFO` for the app and Spring Security; dev profile flips to `DEBUG`

## Boot sequence (Compose `up --build`)

```
1. Compose builds backend, frontend (or frontend.dev), and the three AI images.
2. db starts; healthcheck waits until mysqladmin responds.
3. backend starts (depends_on db: service_healthy); Flyway runs V1..V27 on first boot.
4. ai-recommendation, ai-proposal-analyzer, ai-chatbot start in parallel — no health gate.
5. frontend starts after backend is up.
6. Vite dev container additionally bind-mounts ./frontend → /app for HMR.
```

## Notable design choices for the report

- **One Compose stack covers four runtime languages** (Java, Python, TypeScript, SQL) but maps cleanly to one tier per container — the developer's local workflow is the same shape as a production rollout.
- **Host port 3307 → container 3306** for MySQL is deliberate: most dev machines already have a local MySQL on 3306.
- **Override file for dev** is auto-merged: the production frontend is replaced by a Vite container with HMR, but the rest of the stack is unchanged. Deleting `docker-compose.override.yml` falls back to nginx-served production.
- **`!override` on the frontend `ports` key** in the override file is required because Compose merges port lists by default; `!override` forces the dev port list to replace the production one.
- **All AI services bake their model weights into the image at build time** — first-request latency is constant, not a multi-minute model download.
- **`--preload --workers 1 --threads 4`** is used uniformly across the three AI gunicorns. This keeps a single copy of the model in memory and serves concurrent requests with threads instead of forks.
- **`vector_store/` is a named volume** so the chatbot's FAISS index survives image rebuilds; `recommendation_models/` and `analyzer_models/` likewise preserve trained / downloaded model files.
- **`upload_data` is a named volume** mounted at `/app/uploads`; nothing about uploaded files depends on the host filesystem.
- **`spring.jpa.hibernate.ddl-auto: validate`** enforces a hard contract between Flyway and the entity model — drift is a startup error, not a runtime one.
- **Email and push are off by default** (`APP_EMAIL_ENABLED=false`, `APP_PUSH_ENABLED=false`); this is a deployment-friendly default that requires no SMTP credentials to run the stack end-to-end.
- **Backend → AI service contract is env-driven**, so the same backend JAR runs identically against `localhost:500x` (for IDE-based dev) and against `ai-recommendation:5001` etc. (inside Compose).

## Items to highlight when written up

- Six-service Compose stack: `db`, `backend`, `ai-recommendation`, `ai-proposal-analyzer`, `ai-chatbot`, `frontend`, plus the dev override that swaps the frontend to Vite HMR
- Single `fyp-network` bridge; AI URLs flow as compose service names
- Host port mapping table (with the 3307 / 5173 quirks)
- Named volumes for data persistence (`mysql_data`, `upload_data`, three model volumes)
- Multi-stage backend and frontend builds; AI services bake model weights at build time
- `gunicorn --preload --workers 1 --threads 4 --timeout 180` is the AI runtime profile
- `spring.jpa.hibernate.ddl-auto: validate` couples backend boot to Flyway state
- Env-driven AI URLs and LLM provider chain (`LLM_API_KEY` → `GROQ_API_KEY` → `OPENAI_API_KEY`)
- Email and push are off by default — deployment runs cleanly without secrets
- Vite dev server proxies `/api` and `/uploads` to `localhost:8080`, mirroring production nginx
